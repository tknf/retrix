# 受け入れられたRetrixの変更を実装する

主セッションがこのスキルを実行します。受け入れられた計画、issueの決定、ユーザーの依頼を実装の仕様として使います。

## 手順

1. `AGENTS.md`、受け入れられた計画またはissueの決定、`package.json`のscripts、変わるソースとテスト、いちばん近い既存の実装を読みます。
2. ブランチと作業ツリーを確かめます。出どころの分からない重なる変更があるか、書き込む別のエージェントが動いている時は、編集の前に止めます。
3. 仕様が矛盾しているか、新しい大きな判断が要る時は、止めて必要な判断を報告します。新しい公開の振る舞いを黙って選びません。
4. 認められた範囲だけを実装します。既存の仕組みを使い、差分を小さく保ちます。生成物はプロジェクトのscriptsで作ります。
5. 公開の面が変わる時は、次を同じ変更で直します。
   - `catalog/component-docs`の説明と`catalog/hono-examples`の見本
   - `vp run docs:components`で生成する`docs/components`と`skills/retrix/references/components.md`
   - 関係する`docs/`のガイド
   - `skills/retrix/SKILL.md`
   - `CHANGELOG.md`の`[Unreleased]`
6. 変えた範囲に見合った検証を流します。
   - コードや設定：`vp check`と、変えた振る舞いを確かめるいちばん小さなテスト
   - CSS：`vp run check:css`
   - 見た目や操作：`AGENTS.md`の決まりに従って、変えたコンポーネントのspecだけをChromiumで流す
   - 配布物に関わる時だけ：`vp run build`と`vp run check:package`
7. 差分の全体を読み、変えたパス、コマンドと結果、流していない検証、残った気づき、計画とのずれを報告します。

## 守ること

- 実装を通すために、受け入れ条件やテストを弱めません。
- ずれを隠すために、ワークフローの定義や受け入れた計画を書き換えません。
- ステージ・コミット・push・タグ・公開・issueの編集・さらなる委任をしません。
- 関係のない変更を残し、壊すGitの操作をしません。
