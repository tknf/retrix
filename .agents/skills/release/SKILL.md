# `@tknf/retrix`を公開する

主セッションがこのワークフローを受け持ちます。公開の準備の依頼は、タグの作成やpushを認めたことになりません。公開には、その版を明示した許可が要ります。準備の手順5で、新しい`reviewer`がステージした差分を読みます。それ以外の準備は委任しません。

## 版を選ぶ

- `major`：互換性のない公開API・既定値・振る舞い・HTML構造・クラス名・登録名・動作環境の変更
- `minor`：互換性を保った公開APIやコンポーネントの追加。削除を伴わない非推奨もここに入れる
- `patch`：互換性を保った不具合やセキュリティの修正
- ドキュメントだけ、リポジトリだけの変更では、パッケージの版を上げません。

どう解釈するか迷う時は、ユーザーに版を確かめます。その版とタグがまだ公開されていないことを確かめます。

## 準備

1. レビュー済みで、今の`origin/main`から作った、変更のない公開用のブランチから始めます。
2. `[Unreleased]`の各項目を、公開するコミットと照らし合わせます。項目を`## [X.Y.Z] - YYYY-MM-DD`へ移し、先頭に空の`[Unreleased]`を残します。
3. `vp pm version X.Y.Z -- --no-git-tag-version`を流し、`package.json`とパッケージマネージャーの状態が想定どおり変わったことを確かめます。
4. `vp check`、`vp run check:css`、`vp run test`、`vp run build`、`vp run check:package`を流します。パックされるファイルの一覧、版、exports、パッケージ名を確かめます。流せなかったものは記録します。
5. 公開用のパスだけをステージし、ステージした差分を読み取りだけのレビューにかけます。

## 公開

1. 版`X.Y.Z`を明示した許可を得て、ステージした差分がレビューを通った時のままであることを確かめます。
2. 件名`vX.Y.Zを公開する`と、本文に`検証:`を書いてコミットします。
3. そのコミットに注釈付きタグ`vX.Y.Z`を作ります。
4. fetchしてリモートの状態を確かめ、公開用のブランチとタグをforceなしでpushします。タグで`.github/workflows/release.yml`が動き、npmへ公開します。
5. GitHub Actionsの結果とnpmの版を確かめてから、成功を報告します。

タグを動かしたり使い回したりしません。手動で重ねて公開しません。レジストリの認証情報を出しません。公開ワークフローが目的のdist-tagに対応するまで、プレリリースを公開しません。
