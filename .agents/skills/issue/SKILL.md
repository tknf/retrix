# Retrixのissueを通して受け持つ

主セッションが作業の持ち主です。調査・計画・実装・修正・検証・統合を自分で行います。`$plan`・`$impl`などのスキルを内部の段階として呼びません。

コミット・push・issueの編集・タグ・公開は、ユーザーが認めた操作だけを行います。

## 手順

1. 依頼またはissueの議論の全体、`AGENTS.md`、関係するソース・ドキュメント・テスト・型定義、`package.json`のscriptsを読みます。依頼の前提を今のリポジトリで確かめます。
2. ブランチ、`git status`、未pushのコミット、既存の変更を確かめます。重なる変更の出どころを確かめてから編集し、関係のない変更を残します。
3. 安全に実装するのに要る分だけ計画します。ユーザーに聞くのは、答えで公開の振る舞い・互換性・セキュリティの方針・受け入れ条件・範囲が変わる時だけです。
4. 認められた範囲を実装し、差分が変わるたびに、変えた範囲に見合った検証を流します。
5. 新しい`reviewer`は、ユーザーが求めた時か、セキュリティ・互換性・配布物・公開に大きなリスクがある時だけ使います。指摘は主セッションが確かめて直します。
6. 最後の差分を読みます。変えた範囲に見合った検証だけを流します。入力が変わっていない成功した検証は流し直しません。
7. 明示したパスだけをステージし、ユーザーが認めたコミット・push・issueの操作だけを行います。pushの前にfetchし、force pushはしません。

`researcher`は大きな独立した調べもの、`worker`は他と重ならないパスの機械的な一括編集だけに使います。普通の段階を委任しません。止めるべき指摘を直した後の再レビューは一度までにし、最後の判断は主セッションがします。

出どころの分からない重なる変更、権限の不足、関係する検証の失敗、決まっていない大きな判断、安全に直せない必須の指摘があれば止めます。
