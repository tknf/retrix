# Retrixの変更を計画する

主セッションがこのスキルを実行します。ユーザーが示したissue番号か依頼だけを扱い、issue番号を推測しません。

## 手順

1. `AGENTS.md`、依頼またはissueの議論の全体、関係するドキュメント、変わるソースとテスト、`package.json`のscriptsを読みます。
2. GitHubのissueは、今のコードで前提を確かめてから受け入れます。
3. 今の振る舞いを再現するか、たどります。古い行番号は、シンボルと内容で探し直します。外部のAPIは、入っている型定義か公式のドキュメントで確かめます。
4. 細かな実装の判断は、リポジトリの根拠から決めます。ユーザーに聞くのは、製品・互換性・セキュリティ・ライセンス・範囲の判断で、公開の結果や受け入れ条件が変わる時だけです。
5. 手で確かめることは、結果で範囲や受け入れ条件が変わるなら`blocking`、そうでなければ`observation`に分けます。`blocking`が残ったまま計画を確定しません。
6. 判断や受け入れ条件が多く、issueのコメントでは整理しきれない時だけ、`docs/plans/<issue番号>-<kebab-caseの名前>.md`に一時的な計画を一つ書きます。小さな変更は、会話かissueのコメントで範囲を示せば足ります。
7. 目的、今の根拠、選んだ設計とその理由、変えてよいファイル、変えないもの、リスク、互換性への影響、確かめられる受け入れ条件、検証のコマンドを決めます。

## 守ること

- 実装のコード、テスト、生成物、公開の状態を変えません。
- ユーザーが計画の依頼に含めていない限り、ステージ・コミット・push・タグ・公開・GitHubの編集をしません。
- 仮定の将来の要件のために設計を広げません。
- 秘密情報を含むファイルを読みません。

決めた設計、確かめられる受け入れ条件、変えないもの、手で確かめること、変わるパス、変えた成果物や外部の状態を報告します。
